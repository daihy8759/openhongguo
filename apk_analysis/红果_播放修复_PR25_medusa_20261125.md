# 播放修复（三）：上游 PR #25 就是正解（2026-11-25 09:0x CST）

> 上一轮（`红果_播放复测_设备身份门禁_20261125.md`）把锅扣在「设备身份」上。**那份结论作废**：
> 真正的原因是播放请求被去掉了 `x-medusa`。套用上游
> [beilunyang/openhongguo#25](https://github.com/beilunyang/openhongguo/pull/25) 后，
> **全新匿名设备直接可播**，不需要任何设备档案导入。

## 1. PR #25 说了什么

> 服务端对播放请求的要求在 11 月翻转了：
> - 2026-11-10 之前：`x-medusa` + 有效 551 信封 → 空 200 body，所以要删掉该头；
> - 2026-11-23 起：**必须带** `x-medusa`（设备布局，消息字段 21 = 369），不带就回空 200 body。

本仓库的 `SignPlaybackPOST` 一直有 `delete(headers, "x-medusa")`，正是 11-10 那次观察的产物。
所以旧播放接口（`video_model/v1/`）从 11-23 起必然回空体。

## 2. 复现与验证（本机实测）

## 3. 为什么上一轮会误判成「设备身份门禁」

上一轮的重放矩阵里，**所有"成功"的组合都带着 `x-medusa`，所有"失败"的组合都用了本仓库那台设备**，
两个变量绑在一起、正好被官方设备这一列掩盖：

| 变体（上一轮） | 当时用哪套签名 | 现在知道为什么通/不通 |
|---|---|---|
| 官方 device_id/iid + 完整 query ✅ | V5 签名器（自带 medusa） | medusa 在 → 通 |
| 本仓库 device_id + 完整 query ❌ | 同上 | 当时 V5 路径本身还差条件 → 空 |
| 本仓库 device_id + 旧接口（带 medusa）✅（**本轮补测**） | `SignPlaybackPOST` + PR | 同一台"不受信任"设备照样通 |

也就是说：服务端从没按设备号拉黑我们，是我们在旧接口上把必填头删了。
